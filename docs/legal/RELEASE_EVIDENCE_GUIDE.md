# 发布证据填写与验收指南

版本：2026-09-01
适用版本：照片流 26.8.31 公测版
状态：模板；任何阻断项均未因本文件建立而完成

本指南把 `README.md` 中的五项发布阻断拆成可交付、可复核的证据。它不是法律意见，也不替用户、业务负责人、个人信息保护负责人或律师作事实选择和法律判断。

## 提供方式与证据边界

可以提交到仓库的内容：

- 已由用户或律师确认、准备公开展示的经营者名称、地址类型、联系渠道等公开文本；
- 不包含身份证号、证照影像、签名、密钥、用户数据或控制台秘密的脱敏摘要；
- 受控证据库中的文件 ID、审批日期、批准角色和文件 SHA-256；
- 不含个人数据的测试方法、测试结果摘要及发布归档清单。

不得提交到 Git 的敏感材料：

- 营业执照扫描件、身份证件、个人手机号和非公开住址；
- 已签字的 PIPIA 原件、内部 SOP 全文、劳动或委托关系证明；
- CloudBase 控制台截图、数据库导出、删除日志、权利请求工单和身份核验材料；
- `SecretId`、`SecretKey`、管理 Token、环境 ID 等未批准公开的配置。

上述敏感材料应存放在访问受控、可审计且有备份的内部证据库。仓库只记录类似 `证据文件ID：[待填写]；SHA-256：[待填写]；审批日期：[待填写]` 的索引，不记录可反推出敏感内容的路径或访问凭据。签名原件、证照、身份材料、密钥和 Token 一律不得进入 Git。

## 1. 经营者地址

### 用户需要提供

- 公开文本：经营者全称、选定的地址、地址类型（“营业执照登记地址”或“可正常收件的常用办公地址”）、邮编（如适用）以及生效日期。
- 内部证明：当前有效营业执照，或能证明常用办公地址可正常收件并由经营者控制的材料；律师审阅意见（如有）。
- 选择记录：由用户/业务负责人和律师决定使用营业执照登记地址还是可正常收件的常用办公地址，并记录选择理由和批准日期。本模板不替其选择。

### 验收方法

1. 对照内部证明逐字核验经营者名称和地址，不以搜索结果或历史合同代替原件。
2. 对公开地址做一次可追踪的收件测试，保留寄送日期、签收结果和异常处理记录。
3. 核对安装条款、隐私政策、人脸规则和联系页中的经营者表述一致。
4. 由批准人签署公开文本版本，并在仓库记录内部文件 ID、SHA-256 和审批日期。

## 2. 个人信息权利请求责任人和渠道

### 用户需要提供

- 公开文本：稳定联系邮箱或其他可持续接收请求的渠道、受理范围、预计答复时限和必要的身份核验提示。
- 内部证明：正式指定的责任岗位、岗位邮箱、替补/升级岗位、服务时限（SLA）、身份核验规则和查阅/更正/删除/复制或导出 SOP。
- 联系渠道必须由组织控制，不应依赖无法交接的个人账号。可以沿用现有公开邮箱，但必须先证明其归属、收件监控和交接机制；仓库现有文本不等于已经指定责任人。

## 3. 服务器地域、数据库保存和删除任务

- 公开文本：实际处理地域、保存期限、删除机制和权利行使方式；只能在控制台与演练证据确认后发布。
- 内部证明：环境与地域截图、集合和索引导出、定时触发器配置、部署版本、成功/失败日志、告警、手工补偿记录和抽样验证结果。
- 详细填写、验收和演练使用[数据保存、清理与个人权利请求运行手册模板](DATA_RETENTION_AND_RIGHTS_RUNBOOK_TEMPLATE.md)。
- 建议内部文件名：`LEGAL-03-cloudbase-retention-evidence-<YYYYMMDD>.zip`。

## 4. 人脸信息 PIPIA

- 公开文本：敏感个人信息处理目的、方式、必要性、保存、撤回及未成年人规则；应与最终批准的评估一致。
- 内部证明：完成的评估正文、风险与措施验证材料、业务负责人和个人信息保护负责人签字、日期、版本及复评记录。
- 使用[人脸身份识别个人信息保护影响评估模板](PIPIA_TEMPLATE.md)，但不要把含签名的版本提交 Git。
- 建议内部文件名：`LEGAL-04-face-recognition-pipia-v<版本>-signed.pdf`。
- 验收：字段完整；风险有责任人和验证证据；结论由授权人员填写；签字与日期完整；报告及处理记录的至少三年留存控制已建立。

## 5. 第三方软件发行材料

- 公开文本：最终发行物中每个第三方组件的名称、版本、许可证、版权归属、源码或书面要约获取方式。
- 内部证明：最终安装包/组件包 SBOM、许可证全文、对应源码、补丁、构建参数、上游 commit、每个归档和二进制的 SHA-256、下载记录或书面要约、归档内容清单。
- 使用[第三方发行证据核对表](THIRD_PARTY_DISTRIBUTION_EVIDENCE.md)。
- 建议内部文件名：`LEGAL-05-<release>-sbom.json`、`LEGAL-05-<release>-corresponding-source.zip`、`LEGAL-05-<release>-licenses.zip` 和 `LEGAL-05-<release>-approval.pdf`。
- 验收必须基于最终发行归档本身，不能只看源码仓库。PairDETR/CUDA 等高风险可选包在证明未闭环时不得进入公开发行归档。

## 发布批准记录

只有五项均通过，并且 `release:prepare` 已生成 commit/version 专属不可变 staging 后，才创建非敏感批准索引：复制 `RELEASE_APPROVAL_TEMPLATE.json` 为 `RELEASE_APPROVAL.json`，保持 `schemaVersion: 2`，填写与交付清单匹配的版本、`buildSourceCommit`、`status: "approved"`、ISO UTC 批准日期、最终安装包 SHA-256 和稳定 `DELIVERY-MANIFEST.json` SHA-256。批准索引可在后续独立审批提交中形成；它不改变已经固定的构建源码提交。业务、隐私和法务只填批准角色；五项 blocker 各自填受控证据 ID、SHA-256、批准日期和批准角色。不得把未签名的组件验证回执当作批准或信任根。

当前线上 release 服务仍使用自动文档 ID，不能证明跨机器幂等。每份批准 manifest 只能由一台授权发布机执行；客户端会发送 manifest SHA-256 作为幂等提示，并以本地 pending 记录禁止自动重试，但这不是服务端保证。超时、连接中断、`saved:true` 缺失或“服务端可能已保存但客户端未收到响应”时，必须先由人工在 CloudBase 与本地 pending 记录中核验，禁止换机器或直接重发。
